# ADR 0023: Translating the web app (i18next, Weblate)

- Status: Accepted (2026-10-09). Implementation is W12c.

## Context

Every user-facing string in `apps/web` is an English literal in JSX (about 70 component files),
plus the error texts in `lib/messages.ts`. Dates and numbers already go through `Intl`
(`toLocaleDateString` and friends, mostly with the browser's default locale). There is no
language preference. PLAN §12 asks for i18n plumbing, English string extraction and a Weblate
setup, so that translators can contribute without touching code.

Out of scope here: the quick-add/NLP grammar (`packages/nlp`) stays English (translating date
grammar is a separate, much larger job); server-rendered emails stay English for now; Android
uses its own `res/values/strings.xml`, which Weblate also reads, as a later component.

## Decision

- **Library: `i18next` + `react-i18next`** (both MIT). Messages are flat JSON in **i18next JSON
  v4** format, which Weblate supports natively with CLDR plural suffixes (`_one`, `_other`, …);
  Weblate's own docs recommend v4 when plurals are used. FormatJS/react-intl was the alternative
  (ICU messages, also supported by Weblate since 5.4); i18next was chosen because its plain
  key/value files are easier for volunteer translators and for review in diffs, and its plural
  handling covers what the app needs.
- **Files.** `apps/web/src/locales/en.json` is the monolingual base file; other languages are
  `apps/web/src/locales/<lang>.json`. Keys are dotted by screen (`settings.ai.title`,
  `task.menu.delete`), never the English text itself, so fixing an English typo does not orphan
  every translation. Only English is bundled into the main chunk; other languages load with a
  dynamic `import()` so they become separate hashed files (and the W12a service worker precaches
  them like any other asset).
- **Interpolation is text, not HTML.** Configure i18next with `interpolation.escapeValue:
false`: React already escapes every string it renders as text, and i18next's own HTML
  escaping on top would show `&lt;` to users. The safety rule is therefore on our side: never
  render a translation with `dangerouslySetInnerHTML`, and for a sentence with a link or emphasis
  use the `<Trans>` component with named components. A translation can then only change words,
  not markup (a translator is an untrusted source).
- **Language choice.** A per-user preference `language` (`'auto'` or a BCP 47 tag from the
  bundled list) in `packages/shared/src/preferences.ts`; `'auto'` uses `navigator.languages`.
  The resolved language also sets `<html lang>` and is passed to the `Intl` calls that currently
  pass `undefined`, so dates and plurals match the UI language.
- **Extraction and checks.** `i18next-cli` (the i18next project's own extractor) runs as
  `pnpm --filter @bokydo/web i18n:extract`; CI fails if `en.json` is out of date with the source
  or if a key is missing from it. An ESLint rule (`i18next/no-literal-string` from
  `eslint-plugin-i18next`, ISC) flags new JSX string literals once extraction is complete.
- **Weblate.** One component, file mask `apps/web/src/locales/*.json`, monolingual base file
  `apps/web/src/locales/en.json`, file format "i18next JSON file v4", pushing to a `weblate`
  branch that is merged by pull request like any other change, never straight to `main`. The
  setup steps live in `docs/translating.md` so that either Hosted Weblate (which has a free
  plan for libre projects; check its current terms) or a self-hosted instance can be used; choosing between them is the maintainer's
  call, not part of this ADR.

## Consequences

- Extraction touches nearly every component, so it should land in one pass per area (settings,
  task views, admin, AI screens) on a branch that is current with `main`, to keep merge
  conflicts short-lived.
- Untranslated keys fall back to English, so a partly translated language is usable.
- Screen-reader labels (`aria-label`, live-region messages, toast texts) are strings too and
  must be extracted with the rest; the a11y audit runs again afterwards.
